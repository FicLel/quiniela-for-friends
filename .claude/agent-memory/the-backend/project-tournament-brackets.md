Built the backend for the Tournament Brackets feature (knockout bracket R32→Final with member predictions + results). No new DB tables/migrations — everything is a computed view over existing `matches` and `user_expected_results` tables.

**Why:** approved technical brief required cache-only derived data (group standings, qualification projections, cascade-resolved bracket labels), reusing the existing `TtlCache` (`lib/ttlCache.ts`) rather than inventing new cache infra.

**New module `tournaments/`:**
- `tournaments.types.ts` — GroupProjection, MatchupCard, BracketView, ports (IMatchesReader, IPredictionsReader — narrow slices of competitions/expectedResults read surfaces, not the full repo interfaces)
- `GroupProjectionService.ts` — pure brute-force combinatorial projection (≤27 outcome combos per group). Key design point: only WINNER/RUNNER_UP are auto-qualifying slots; THIRD_PLACE is treated as non-qualifying in this single-group model because third-place advancement is a cross-group mechanism this projection has no visibility into — landing only in THIRD_PLACE/NONE slots across all combos still resolves to ELIMINATED, not QUALIFIED. This was a real bug caught by tests (initial version wrongly auto-qualified 3rd place).
- `BracketCascadeService.ts` — parses `matchupDescription` strings ("Group A Winner vs Group B Runner-up", "Winner R32_01 vs Winner R32_02") to derive display-only team names. Group-based placeholders resolve from GroupProjection; bracket-reference placeholders (Winner/Loser <SLOT>) resolve ONLY from confirmed regulationHomeGoals/AwayGoals on the referenced bracketSlot, never from projections. Pure function, never mutates input Match objects or writes to DB.
- `TournamentBracketCache.ts` — wraps TtlCache in two module-level singletons (Layer 1: global skeleton, 1-entry cache; Layer 2: per `${quinielaId}:${userId}`, 500-entry LRU). Class instances all share the same module-level TtlCache singletons (matches the existing `matchesCache`/`playerPredictionsCache` pattern) — tests MUST call `resetTournamentBracketCache()` in `beforeEach`, not just construct `new TournamentBracketCache()`, or tests leak state across each other.
- `TournamentBracketService.ts` — orchestrator with access gate (`isApprovedMember`), Layer1 rebuild-once-and-reuse, Layer2 read-through cache. Constructor takes `(matchesReader, predictionsReader, membershipsRepository, groupProjectionService, cascadeService, predictionModeReader, cache?)`.

**Two critical bugs found post-implementation by implementation-validator, both fixed:**
1. **Prediction-mode blindness.** This app has a global `PredictionMode` ('shared' vs 'per_quiniela', see `appSettings.types.ts`) — 'shared' mode predictions have `quiniela_id IS NULL` in `user_expected_results`. The first version of `TournamentBracketService` always called `findByUserIdAndQuiniela(userId, quinielaId)` with a real quinielaId, which returns `[]` in shared mode (the actual app default) — silently hiding every prediction on the bracket. Fix: added `IPredictionModeReader` port (matches `IAppSettingsService.getSettings()` shape) and branch exactly like `app/[lang]/(private)/welcome/page.tsx:79-136` does — 'per_quiniela' reads `findByUserIdAndQuiniela`, 'shared' (and the safe-default fallback on settings failure) reads `getExpectedResultsForUser` (named to match `IExpectedResultsService`'s real method, not `IExpectedResultsRepository`'s `findByUserId` — services should depend on services, not repos, per architecture rules). Verified the real `ExpectedResultsService`/`AppSettingsService` satisfy these ports structurally with zero adapter code via a throwaway typecheck file.
2. **False-positive group qualification under goal-margin sensitivity.** The original `GroupProjectionService.simulateFixture` always simulated remaining fixtures with a fixed ±1 goal margin (1-0/0-0/0-1). This missed cases where the true qualification outcome depends on the SIZE of a win, not just W/D/L — e.g. two teams tied on points where one's GD-overtake of the other depends on whether a remaining fixture is a 1-0 squeaker or a 6-0 blowout. Fixed by testing each remaining fixture at multiple margins (`WIN_MARGINS = [1, 12]`) and relying on monotonicity (more goals for the same outcome can only help that team's GD, all else fixed) — if the verdict agrees at both margin extremes it's safe for everything between/beyond; if it disagrees, report `UNDECIDED` rather than guess. Caught via a deliberately constructed repro (4-team group, two teams points-tied for the 2nd spot, one has a remaining fixture whose margin alone decides which of the two advances) before writing the regression test — confirmed the old code asserted a false positive, the new code correctly reports `UNDECIDED`, and a sanity test confirms a real blowout result does flip the outcome (proving `UNDECIDED` isn't just overly conservative).

**Invalidation hooks wired into existing infra (not new files):**
- `competitions/CompetitionsRepository.ts` — added `tournamentBracketCache.invalidateLayer1()` + `clearLayer2()` calls in `upsertMatches`, `upsertKnockoutPlaceholders`, `updateRegulationResults`, `updateKnockoutTeams` (all matches-table writes).
- `expectedResults/ExpectedResultsRepository.ts` — added `invalidateBracketCacheForWrite` private method called at the end of `upsert()`. For per-quiniela predictions (quinielaId set): single-key invalidate. For shared predictions (quinielaId null): fans out by querying `quiniela_memberships` for all the user's approved quinielas and invalidating each — mirrors the existing fan-out pattern in `PredictionScoreRepository.findPredictionsWithQuinielas`.

See [[feedback-fix-existing-tests-when-mocks-break]] — had to update `ExpectedResultsRepository.test.ts`'s `mockFrom`/`mockSelect` to handle the new `quiniela_memberships` query path triggered by every `upsert()` call now, even existing tests that don't care about bracket caching.
